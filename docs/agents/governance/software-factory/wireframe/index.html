Annotations — the parts a wireframe must state

  • Purpose: settle the shape of the phase report before building it — specifically whether the answer can be trusted without reading the code.
  • Screen: a terminal report, not a GUI. The operator reads it where they already are. Serves US-1 and its three acceptance scenarios.
  • State shown: three repos at once, because US-1's independent test is "three repos in genuinely different states get three different, correct answers." One example would not show that.
  • Deliberately absent: colour for status, icons, progress bars, a dashboard. A GUI here would imply the phase is something to look at rather than something to act on.
  • Not wired: nothing runs. The output is hand-written to show the shape.
  • Interactions to design against: (1) is the phase the first line, readable at a glance? (2) can a wrong answer be argued with from the evidence alone? (3) does --json need a different shape, or the same one?
